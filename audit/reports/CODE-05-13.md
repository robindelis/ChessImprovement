# CODE-05-13 — Test output is 45% ad-hoc narrative `print`; a real failure traceback is buried
- **Severity:** low
- **Type:** ui-regression
- **File:** `tests/test_user_behavior_probe.py`
- **Line(s):** 32 print calls throughout; also `tests/test_user_workflows.py` (13 calls), `tests/test_timeline_spam.py:13-14`
- **Component:** Test suite
- **Repro script:** `unittest discover tests` output capture (see "Actual")
- **Detected by:** CODE-5

## Expected
A test suite prints progress dots, then `Ran N tests` / `OK` or a failure traceback. Narrative logging goes to a captured stream, not stdout.

## Actual

```

$ ... | grep -cE '^\s*(\[STEP|=+ [A-Z0-9 ]|SCENARIO|RUNNING WORKFLOW|✓|✔)'
```

45% of the output is narrative noise. `print()` calls per collected test file:


The tail of a passing run looks like this, and the actual result is on the *last* line:

```
  [STEP 2: PREDICT EXPECTED BEHAVIOR] Black trainer presents position after 1. e4, user plays 1... c5, gets correct=True.
```

Sample noise from `test_user_behavior_probe.py`:
```
==== SCENARIO 3: Chessbook-Style Repertoire Mastery Progress ====
Overall Progress (All Studies): {'repertoire': 'white', 'filter_study': None, 'total_moves': 5, 'mastered_count': 2, ...
```

These are attacker-agent artefacts (`[STEP n: THINK OF AN ACTION]` is a prompt-format convention from `audit/BRIEF.md`) that were left in the suite as if they were unit tests. `test_user_behavior_probe.py` and `test_timeline_spam.py` match the `test*.py` discovery pattern, so they are the only reason 45% of the output is noise.

## Root cause
Narrative scaffolding from the prior interactive audit rounds was committed as discoverable tests without stripping the `print()` layer. `unittest` does not capture stdout by default, so it all lands in the same stream as the result summary.

## Exploit / escalation
1. In CI or a fixer-agent context, the last 100 lines of a run are `✓ Scenario N passed…`; a single `AssertionError` scrolls off the top of a 191-line wall and gets missed, so a genuinely red suite is read as green.
2. `tests/test_user_workflows.py:17-18` and `tests/test_timeline_spam.py:13-14` also use `print`, but their step numbering restarts per test, making output ambiguous about which test produced which line.
3. Adjacent variants with the same root cause (test-only debug output left in place):
   - `tests/test_setup.py:40-41` prints `"Warning: Failed to copy production DB to test DB: …"` and continues, so a degraded isolation run looks like a normal one (see CODE-05-07).
   - `backend/db.py:239, 295, 297, 320` print warnings from inside `init_db()`/`migrate_studies_and_cleanup_blunders` on **every** boot; `start.py` output is piped into the Electron console by `electron/main.js:101-109`, so migration failures surface only in a console the user never opens.
   - `backend/lichess_client.py:55, 57` `print("Lichess token invalid or expired.")` / `print(f"Error fetching Lichess account: {e}")` — the second leaks the exception text (potentially including the request URL) into stdout.
