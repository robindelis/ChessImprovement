# CODE-02-05 — Drawn games are stored as `NULL` in `games.result` and reported to the UI as **losses** with score `0-1`
- **Severity:** high
- **Type:** wrong-result
- **File:** `backend/api.py` (writer at 242, reader at 341-351)
- **Line(s):** api.py:242, 341-351; also `backend/repertoire.py:1479, 1571, 1724, 1832`
- **Component:** Recent Games list
- **Repro script:** `audit/scripts/CODE-2_results.py`
- **Detected by:** CODE-2

## Expected
The `result` column should hold a stable, self-describing token — `'win' | 'loss' | 'draw'`
or at least the literal `'draw'` — and the reader and writer must agree on it. A draw must
never render as a loss.

## Actual
Every writer stores Lichess's **`winner`** field verbatim:

```python
# backend/api.py:242
result = g.get("winner", "draw") if "winner" in g else "draw"
```

```python
# backend/repertoire.py:1479 / 1571 / 1724 / 1832
user_color, g.get("winner", "draw"),
```

Lichess's game export sets `"winner"` to `"white"`, `"black"`, or **`null`** for draws
(the key is present, the value is `null`). `dict.get(k, default)` therefore returns `None`
— the `"draw"` default is unreachable for a real draw.

The reader, however, expects the *literal string* `"draw"`:

```python
# backend/api.py:341-351
raw_result = (row.get("result") or "").lower()

if raw_result == user_color:
    result = "win"
    score_text = "1-0" if user_color == "white" else "0-1"
elif raw_result == "draw":
    result = "draw"
    score_text = "½-½"
else:
    result = "loss"
    score_text = "0-1" if user_color == "white" else "1-0"
```

`row.get("result") or ""` turns `None` into `""`, which falls into the `else` branch →
`loss`.

Observed (`audit/scripts/CODE-2_results.py`):

```
GET /api/games/recent?limit=100 -> 200
  id=ztest_draws  stored_result='NULL' user_color=white  ->  api result='draw' score=½-½
  id=ztest_draw   stored_result='NULL' user_color=white  ->  api result='loss' score=0-1
```

Two rows for the same drawn game, one written as the literal `'draw'` (correct) and one as
`NULL` (what every real sync writes) — the `NULL` one is reported as a **loss with score
0-1**.

Corroboration from the production data copy: `SELECT result, COUNT(*) FROM games GROUP BY result`
yields only `'white'` (157), `'black'` (138) and `'draw'` (12). The 12 `'draw'` rows are
legacy; the 295 winner-colour rows are the current writers, and none of the games a sync
has written recently with `"winner": null` is distinguishable from a loss.

## Root cause
A Lichess API field (`winner`, nullable, colour-valued) is persisted into a column whose
reader expects a game-outcome token. There is no normalisation step and no `NOT NULL`
constraint on `games.result` (`db.py:49`).

## Exploit / escalation
1. Win-rate and result filters built on `games.result` silently drop every draw into the
   loss bucket — any future stats view inherits the same 100 %-wrong draw handling.
2. Adjacent: `result` is also what `GET /api/dashboard`'s `GROUP BY result, user_color`
   (`api.py:462`) aggregates on, so the dashboard's win/loss/draw breakdown is wrong for
   every game synced since the writer was written.
3. Adjacent: `score_text` is computed as `"0-1" if user_color == "white" else "1-0"` in the
   `else` branch, so a `NULL` result for a **black** user renders `1-0` — the *opposite* of
   the convention used in the `win` branch. A fix must handle both branches symmetrically.
