# CODE-02-18 — `init_db()` runs a full-table rewrite migration over `explorer_cache` on every boot, twice per boot, with per-row failures swallowed
- **Severity:** medium
- **Type:** spec-violation (perf + silent data rewrite)
- **File:** `backend/db.py`, `backend/api.py`, `start.py`
- **Line(s):** db.py:210-228; api.py:74-76; start.py:19
- **Component:** Startup migration
- **Repro script:** `audit/scripts/CODE-2_routes.py` (section 6)
- **Detected by:** CODE-2

## Expected
A one-off data normalisation should be gated by a version marker so it runs once. Rows
that cannot be parsed should be reported.

## Actual
Every call to `init_db()` unconditionally selects *every* cached row that does not already
carry the marker, parses its JSON, possibly negates every move's eval, and writes it back:

```python
# backend/db.py:210-228
# Migration: Ensure explorer_cache adheres to White-perspective eval convention
try:
    cursor.execute("SELECT fen, ratings, data_json FROM explorer_cache WHERE data_json NOT LIKE '%\"eval_convention\": \"white\"%'")
    for row in cursor.fetchall():
        fen_val = row["fen"]
        ratings_val = row["ratings"]
        try:
            d = json.loads(row["data_json"])
            parts = fen_val.strip().split()
            if len(parts) >= 2 and parts[1] == 'b':
                for m in d.get("moves", []):
                    if m.get("eval") is not None:
                        m["eval"] = -m["eval"]
            d["eval_convention"] = "white"
            cursor.execute("UPDATE explorer_cache SET data_json = ? WHERE fen = ? AND ratings = ?", (json.dumps(d), fen_val, ratings_val))
        except Exception:
            pass
except Exception:
    pass
```

Problems:

1. **No version gate.** There is no `PRAGMA user_version`, no migration ledger table, and
   no `ALTER`-style marker — the only "already done" signal is a *substring of the data
   itself*. `explorer_cache` is the fastest-growing table in the app (one row per visited
   position per `ratings` string), so the `SELECT … NOT LIKE` is a **full table scan with a
   `LIKE '%…%'` (non-indexable, leading wildcard) on every row**, on every process start.
2. **Runs twice per boot** (see CODE-02-07: `start.py:19` and `api.py:74-76`), so the scan
   and any rewrites are paid twice.
3. **The whole rewrite is one implicit transaction** committed by `db.py:241`, so a large
   cache produces a single large WAL write.
4. **Both `except` clauses `pass`.** A row whose `data_json` is corrupt is skipped forever
   with no log, and — because the marker is never written — it is re-attempted on every
   subsequent boot. A row that fails *mid-loop* (after some `m["eval"]` entries were
   negated in memory but before the `UPDATE`) is not persisted, so it is not corrupted, but
   it is also never repaired.

## Root cause
A data-shape fix was expressed as an unconditional, data-driven migration instead of a
versioned one, and the failure paths were silenced with bare `pass`.

## Exploit / escalation
1. After browsing a few hundred positions, every app launch pays two full
   `LIKE '%…%'` scans of `explorer_cache`; the second boot's scan is guaranteed to find
   zero matching rows but still costs a full scan.
2. Any row whose JSON contains the marker text inside a *value* (e.g. an opening name
   literally equal to `"eval_convention": "white"`) is permanently skipped by the migration.
3. Adjacent: the same `try/except Exception: pass` idiom is used for the five
   `ALTER TABLE` migrations at `db.py:86-90` and `db.py:138-154`, where it hides a genuine
   "database is locked" failure and lets the app start with a half-migrated schema
   (see CODE-02-22 item 6).
