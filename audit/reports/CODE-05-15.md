# CODE-05-15 — `is_important` is `int` on `/api/repertoire/tree` but `bool` on `/api/repertoire/train/next` and `/api/repertoire/train/attempt`
- **Severity:** low
- **Type:** wrong-result
- **File:** `backend/repertoire.py`
- **Line(s):** route `/api/repertoire/tree` returns raw rows (`backend/repertoire.py:1284-1293`); trainer coerces with `bool(...)`
- **Component:** API contract / documentation
- **Repro script:** `audit/scripts/CODE-05_contract_diff.py`
- **Detected by:** CODE-5

## Expected
One type per field across the API. `AGENTS.md:176` states:
> `is_important` (INTEGER): `1` if marked as priority move for opening trainer, `0` default.

Actual observed shapes for the same column:

```
### is_important: tree says? ###
  is_user_move=1      is_important=0      san=e4        # <-- int (raw sqlite row)
  is_user_move=0      is_important=0      san=e6

### /api/repertoire/train/next ###
is_important = False bool

### /api/repertoire/train/attempt ###
is_important = False | next_is_important = False
```

`/api/repertoire/tree` serialises `dict(r)` straight out of `sqlite3` (`backend/repertoire.py:1210, 1219`), so `is_important` is the raw `0`/`1` INTEGER. The trainer paths build an explicit dict and pass it through `bool(...)`, so the same logical field arrives as `true`/`false`. The same split applies to `is_user_move` (raw `0`/`1` from `/api/repertoire/tree`) and to `is_favorite` in `GET /api/scout/recent` (raw INTEGER — `frontend/scout.js:431` has to write `!!item.is_favorite`).

## Root cause
`/api/repertoire/tree` has no serialisation layer; it hands SQLite rows to FastAPI. Every other endpoint constructs its payload explicitly and normalises the flag. There is no response model (`response_model=`) on any repertoire route to enforce the shape.

The frontend currently tolerates the inconsistency because it coerces at every use site:
```
frontend/repertoire_builder.js:1533:  const isImportant = repMove ? Boolean(repMove.is_important) : false;
frontend/repertoire_builder.js:3019:  is_important: Boolean(m.is_important),
frontend/repertoire_builder.js:3079:  is_important: Boolean(m.is_important),
frontend/scout.js:683:              existingImportant = Boolean(repMove.is_important);
```
but `frontend/repertoire_trainer.js:476` and `:749` do **not** coerce:
```javascript
badgeEl.style.display = data.is_important ? 'inline-flex' : 'none';
badgeEl.style.display = data.next_is_important ? 'inline-flex' : 'none';
```
Those happen to read the trainer endpoints, which are the ones that return real booleans, so the split currently works out — by luck of which endpoint each consumer happens to use.

## Exploit / escalation
1. Truthiness works for both `0`/`1` and `false`/`true`, so the current code is not broken — but a consumer that does `if (move.is_important === true)` or renders `${move.is_important}` gets `0`/`1` from `/api/repertoire/tree` and `true`/`false` from the trainer.
2. Because `AGENTS.md:176` documents only the INTEGER form, a fixer implementing a new consumer from the doc will write `=== 1` and break against the trainer endpoints, or `=== true` and break against the tree.
3. Adjacent variants with the same root cause (raw SQLite rows leaking through the API with no response model):
   - `/api/repertoire/tree`'s `moves_by_parent` also leaks `created_at` (unix seconds) while `/api/games/recent` returns `played_at` (also seconds) and `/api/scout/recent` returns `scouted_at` (seconds) — consistent by luck, but nothing enforces it, and `frontend/repertoire_builder.js` mixes them freely.
   - `tests/test_repertoire.py:270` asserts `self.assertEqual(meta_res["is_important"], 1)` (int) while `tests/test_pedagogical_trainer.py:64` and `tests/test_api.py:326` assert the same field as `1` from the write path and `test_user_workflows.py` treats it as a bool — the tests encode both conventions without noticing.
