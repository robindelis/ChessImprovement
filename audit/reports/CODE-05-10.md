# CODE-05-10 — Prior-audit scripts live in `tests/`, are excluded from `unittest discover`, fail open to the production DB, and three import `backend` before `tests.test_setup`
- **Severity:** medium
- **Type:** spec-violation
- **File:** `tests/attack_fixes_abuse.py`
- **Line(s):** 21, 27, 359, 400-412; `tests/reattack_probe.py:10-13`; `tests/attack_round4_deep_abuse.py:23-31`
- **Component:** Test suite / tooling hygiene
- **Repro script:** static grep (see "Actual")
- **Detected by:** CODE-5

## Expected
`audit/BRIEF.md:84-87` calls these "**earlier** audit rounds … read them for context". They are probe artefacts, not part of the regression suite, and per `AGENTS.md:282-288` and `audit/BRIEF.md` hard rule 2, every probe script must `import tests.test_setup` as its **first** backend-adjacent import and must never default to the production database.

```python

...
```

That default is a **relative** path, so it resolves against the CWD, not the repo root. These are the only places in the repository that touch SQLite without going through `backend.db.get_db()`.

Three scripts also violate the documented import order:

```python
# tests/reattack_probe.py:10-13
from backend.db import get_db                          # <-- backend imported FIRST
from backend.repertoire import RepertoireManager, normalize_fen
                                                        
import tests.test_setup                                # <-- isolation set up AFTER
```

```python
# tests/attack_round4_deep_abuse.py:23-25
from backend.repertoire import normalize_fen            # <-- backend imported FIRST
                                                        
import tests.test_setup
```

In the current code this is *not* an actual production write, because `backend/db.py:18` re-reads `os.environ["CHESS_DB_PATH"]` on every `get_db()` and neither module opens a connection at import time — the `unittest discover` run is provably safe (I checksummed `chess_improvement.db` before and after: `sha256` and `mtime` both unchanged). The hazard is structural, not realised: the guarantee depends on `import tests.test_setup` not raising, and `tests/test_setup.py` is **untracked** (`?? tests/test_setup.py`), so the exact file every script's safety depends on is the one file a fresh clone is most likely to be missing.

Two scripts are additionally stale — `tests/repro_bugs.py` and `tests/verify_patches.py` are near-duplicates (169 vs 131 lines) asserting the same already-fixed bugs, and both patch `backend.api.LichessClient.fetch_user_games` for a `/api/sync` route whose real implementation moved. And `tests/verify_patches.py` and `tests/repro_bugs.py` are byte-for-byte redundant in their first 30 lines (the same `RequestAdapter` shim), which is how the `requests`-shadowing trick got copied nine times.

## Root cause
Probe scripts were written into `tests/` rather than a separate directory, and each invented its own `RequestAdapter` shim instead of sharing a helper. The duplicated shim (nine copies) is why the fail-open `DB_PATH` default and the import-order violation were replicated rather than fixed once. The fail-open default (`os.environ.get(..., "chess_improvement.db")`) inverts the intended safety direction: the safe value should be the fallback, not the override.

## Exploit / escalation
1. `cd /tmp && python /home/robin/Projects/ChessImprovement/tests/attack_fixes_abuse.py` — if `CHESS_DB_PATH` is unset, `sqlite3.connect("chess_improvement.db")` creates a stray DB in `/tmp` (or, from the repo root, opens and mutates the real one), and `DELETE FROM repertoire_moves WHERE repertoire='black'` wipes the user's Black repertoire.
