# CODE-02-17 — A "good alternative" trainer answer increments `successes` but never advances `interval_days`/`next_review_date`, and `ease_factor` is never updated
- **Severity:** medium
- **Type:** wrong-result
- **File:** `backend/api.py`
- **Line(s):** 684-701 (spaced-repetition state), 708-741 (alternative branch), 744-754 (upsert)
- **Component:** `POST /api/train/evaluate_move` (spaced repetition)
- **Repro script:** n/a (static read of the SM-2 variant)
- **Detected by:** CODE-2

## Expected
A correct answer by any acceptable route (the engine's top move *or* a move within the
tolerance) should advance the schedule: longer interval, later `next_review_date`, and
eventually `status = 'mastered'`.

## Actual
The state is loaded, then only two of the three branches touch the schedule:

```python
# backend/api.py:685-690
now = int(time.time())
attempts = (blunder["attempts"] or 0) + 1
successes = (blunder["successes"] or 0)
interval = blunder["interval_days"] or 1.0
ease = blunder["ease_factor"] or 2.5
status = "learning"
```

Best-move branch — schedule advances:

```python
# backend/api.py:696-702
if is_exact_best:
    successes += 1
    status = "mastered" if successes >= 2 else "learning"
    interval = min(interval * ease, 3650.0) if successes > 1 else 1.0
    next_review = now + int(interval * 86400)
```

Good-alternative branch — `successes` increments but **neither `interval` nor `status` is
touched**:

```python
# backend/api.py:724-730
if cpl_diff <= 35:
    successes += 1
    feedback_type = "good_alternative"
    diff_str = f"+{abs(cpl_diff)}" if cpl_diff < 0 else f"-{cpl_diff}"
    feedback_msg = f"Good alternative: {user_san} (Diff: {diff_str} cp). ..."
    status = "learning"
    next_review = now + 86400
```

`interval` keeps whatever value it was loaded with, and the upsert persists it unchanged:

```python
# backend/api.py:744-754
INSERT INTO drill_reviews (blunder_id, attempts, successes, last_attempt_date, next_review_date, interval_days, ease_factor, status)
VALUES (?, ?, ?, ?, ?, ?, ?, ?)
ON CONFLICT(blunder_id) DO UPDATE SET
    attempts = excluded.attempts,
    successes = excluded.successes,
    last_attempt_date = excluded.last_attempt_date,
    next_review_date = excluded.next_review_date,
    interval_days = excluded.interval_days,
    status = excluded.status
```

Consequences:

1. A user who always answers with a good (but not engine-top) move accumulates
   `successes` without ever reaching `status = 'mastered'` — the `'mastered'` transition
   only exists inside the `is_exact_best` branch (`api.py:698`).
2. `interval_days` never grows for that card, and `next_review_date = now + 86400`, so the
   card is permanently due every single day. The trainer can never "drain" such a card.
3. `ease_factor` is read (`api.py:689`) and written (`api.py:754`) but is **absent from the
   `DO UPDATE SET` list** — it is therefore permanently frozen at the schema default
   (`2.5`, `db.py:103`). The SM-2 ease factor is a constant.
4. The `suboptimal` and `engine_error` branches (731-739) also write `status = "learning"`
   (from line 690), which means a **wrong** answer *downgrades* a `'mastered'` card — a
   deliberate-looking lapse, but it is applied identically to the `engine_error` case where
   the user did nothing wrong.

## Root cause
The SM-2 schedule is implemented as ad-hoc per-branch assignments rather than as a single
`review(state, quality) -> new_state` function applied to all feedback types. The
`ease_factor` omission in the `ON CONFLICT` clause is the classic symptom of the same
divergence.

## Exploit / escalation
1. Answer a blunder 20 times with moves within 35 cp of the engine's choice: the UI reports
   "Good alternative" each time, `successes` climbs, but the card never leaves the
   "due today" queue and the progress percentage never moves.
2. `GET /api/train/paths` `due_today` (`api.py:617-620`) and `GET /api/dashboard`
   `due_reviews_count` (`api.py:448`) will therefore report a permanently non-zero
   backlog that can never be cleared.
3. Adjacent: `attempts`/`successes` are incremented before the `INSERT`, so an interrupted
   request (client abort mid-response) still commits the increment — the "prevents silent
   progress loss" comment at `api.py:743` describes the upsert, but the counter
   derivation is not idempotent.

(Note: per CODE-02-03 the whole `/api/train/*` surface is frontend-orphaned today, so this
is latent rather than user-visible — but it is the only remaining writer of the schedule,
so it will become live the moment the trainer is reconnected.)
