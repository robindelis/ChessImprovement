# CODE-02-09 — A new Stockfish process is spawned per request with no pool, semaphore, or cap; N concurrent requests = N × (2 threads + 64 MB hash)
- **Severity:** high
- **Type:** spec-violation (resource exhaustion)
- **File:** `backend/api.py`, `backend/analyzer.py`, `backend/evaluator.py`
- **Line(s):** api.py:218 + 268, api.py:710 + 741, analyzer.py:22-37, evaluator.py:67-73
- **Component:** Engine lifecycle
- **Repro script:** `audit/scripts/CODE-2_sse.py` (section D)
- **Detected by:** CODE-2

## Expected
There should be exactly one bounded pool of engine processes (the codebase already has
the right pattern in `AsyncEngineEvaluator`, a singleton with a lock), and every route that
touches the engine should go through it.

## Actual
The only pooled/singleton engine is the *async* evaluator. Every other engine user builds
its own from scratch, per request:

```python
# backend/api.py:710 / 741  (POST /api/train/evaluate_move, the "alternative move" branch)
analyzer = GameAnalyzer()
try:
    eng = analyzer._get_engine()
    ...
finally:
    analyzer.close()
```

```python
# backend/api.py:218 / 268  (POST /api/sync)
analyzer = GameAnalyzer()
...
analyzer.close()
```

and `GameAnalyzer._get_engine` is an uncached process spawn:

```python
# backend/analyzer.py:22-29
def _get_engine(self):
    if self._engine is None:
        if not os.path.exists(self.stockfish_path):
            raise FileNotFoundError(f"Stockfish binary not found at {self.stockfish_path}")
        self._engine = chess.engine.SimpleEngine.popen_uci(self.stockfish_path)
        self._engine.configure({"Threads": 2, "Hash": 64})
    return self._engine
```

There is **no** `GameAnalyzer` singleton, no semaphore, no `maxsize` on the process, and
no authentication or rate limit on any of the routes that reach it. FastAPI's sync
`def` routes run in the default `AnyIO` thread pool (up to 40 threads), so up to 40
simultaneous `POST /api/sync` calls → 40 Stockfish processes → 80 engine threads and
~2.5 GB of hash memory, on top of the shared `AsyncEngineEvaluator` process.

The frontend makes concurrent engine-touching requests easy: *Sync & Analyze*
(`repertoire_builder.js:666` → `/api/repertoire/sync_games_stream`) and *Sync Recent*
(`repertoire_builder.js:1113` → `/api/games/sync_recent_stream`) are independent buttons,
and `eval_stream` is fired on every board navigation
(`repertoire_builder.js:1756`, `scout.js:1930`).

## Root cause
Two independent engine abstractions (`GameAnalyzer` sync / `AsyncEngineEvaluator` async)
with opposite lifecycle policies. The sync one is a per-instance disposable, and the
routes construct it inline.

## Exploit / escalation
1. Unauthenticated `for i in $(seq 1 20); do curl -X POST 'localhost:38281/api/sync?max_games=1' & done`
   → 20 concurrent UCI handshakes, 20 processes; combined with the ~30 min depth-12
   analysis each game needs, the host is pinned.
2. `POST /api/train/evaluate_move` pays a **full process spawn + UCI handshake + quit** per
   non-best-move attempt — the trainer's most common interaction is the most expensive one.
3. Adjacent: the `_get_engine()` reach-through at `api.py:712` couples a route to a
   private method, so any change to `GameAnalyzer`'s engine lifecycle silently breaks the
   API. `analyzer.close()` is in a `finally`, so the process *is* released on the happy and
   error paths — but not on `KeyboardInterrupt`/`SystemExit` raised before `finally` is
   entered.
