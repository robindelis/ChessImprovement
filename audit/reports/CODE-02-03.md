# CODE-02-03 — The entire legacy blunder-trainer surface (`/api/blunders*`, `/api/train/*`, `drill_reviews`) is frontend-orphaned, yet writes a row per analyzed blunder
- **Severity:** medium
- **Type:** spec-violation
- **File:** `backend/api.py`, `backend/analyzer.py`, `backend/db.py`
- **Line(s):** api.py:434-485, 487-535, 537-582, 584-627, 629-792; analyzer.py:244-249; db.py:94-107
- **Component:** REST API surface / spaced-repetition subsystem
- **Repro script:** `audit/scripts/CODE-2_routes.py` (section 5)
- **Detected by:** CODE-2

## Expected
Either the UI consumes these endpoints, or they are removed. A subsystem that nothing
reads should not write to the database on the hot analysis path.

## Actual
Grepping every `fetch(...)` in `frontend/*.js`, `frontend/*.html` and `electron/*.js` for
each registered route path yields:

| Route | Called from |
|---|---|
| `GET /api/blunders` | **nowhere** |
| `GET /api/blunders/{blunder_id}` | **nowhere** |
| `GET /api/train/paths` | **nowhere** |
| `POST /api/train/evaluate_move` | **nowhere** |
| `GET /api/dashboard` | `electron/main.js:63` — **status code only**, as a liveness probe |

`electron/main.js:61-73` reads nothing but the status code:

```js
const req = http.get(`${SERVER_URL}/api/dashboard`, { timeout: 1500 }, (res) => {
    resolve(res.statusCode >= 200 && res.statusCode < 400);
});
```

Yet `/api/dashboard` runs 7 aggregate queries (two `COUNT(*)` on `games`/`blunders`, two
on `drill_reviews`, a `GROUP BY opening_name, color` over the whole `blunders` table
joined to `games`, a `GROUP BY result, user_color`, and a 5-row `ORDER BY b.created_at`
join) — **every 250 ms** for up to 25 s while the desktop app boots
(`electron/main.js:76-79`).

All 7 `drill_reviews` references in `api.py` live in those orphaned routes:

```python
cursor.execute("SELECT COUNT(*) as count FROM drill_reviews WHERE status = 'mastered'")   # 445
cursor.execute("SELECT COUNT(*) as count FROM drill_reviews WHERE next_review_date <= ?", ...) # 448
LEFT JOIN drill_reviews d ON b.id = d.blunder_id                                          # 503, 547, 609, 637
SELECT COUNT(*) as due_count FROM drill_reviews WHERE next_review_date <= ?               # 618
INSERT INTO drill_reviews (...)                                                           # 745
```

and `backend/repertoire.py` — the *only* live repertoire code — never touches
`drill_reviews` at all (`grep -n drill_reviews backend/repertoire.py` → no hits).
Nevertheless every detected blunder still inserts a spaced-repetition row:

```python
# backend/analyzer.py:244-249
cursor.execute("""
INSERT OR IGNORE INTO drill_reviews (
    blunder_id, attempts, successes, last_attempt_date, next_review_date, interval_days, status
) VALUES (?, 0, 0, 0, ?, 1.0, 'new')
""", (blunder_id, int(time.time())))
```

## Root cause
A feature was replaced (Chessbook-style repertoire trainer) but the previous
blunder-drill feature's HTTP surface, its `drill_reviews` table, and its per-blunder
write were left in place. The only live consumer of `/api/dashboard` wants a health
signal, not the payload.

## Exploit / escalation
1. Cost: ~300 lines of unmaintained route code plus one extra `INSERT` per blunder, for
   zero user-visible benefit.
2. Risk: `POST /api/train/evaluate_move` is the only remaining writer of
   `drill_reviews.attempts/successes`. It is reachable by any unauthenticated client
   (CORS is `allow_origins=["*"]`, `api.py:56-62`) and would happily mutate state, so
   removing it is also a small hardening win.
3. Adjacent: `/api/dashboard` being a live health endpoint means the 250 ms Electron poll
   keeps two `COUNT(*)` full scans plus a `GROUP BY` warm in the page cache during every
   app start; on a large `blunders` table this is a needless startup I/O cliff.
