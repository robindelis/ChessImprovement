# CODE-02-11 — `POST /api/sync` converts every failure into HTTP 200 with a different response shape, and leaks the engine + DB connection on the error path
- **Severity:** medium
- **Type:** spec-violation / crash
- **File:** `backend/api.py`
- **Line(s):** 212-214, 261-269, 271-275
- **Component:** `POST /api/sync`
- **Repro script:** `audit/scripts/CODE-2_repro.py` (PROBE 6)
- **Detected by:** CODE-2

## Expected
A total failure (auth failure, network error, HTTP 429 from Lichess, missing engine
binary) should be a non-2xx status with a stable error body. Success and failure must
share the same response shape, or clients must be able to branch on it. Resources must be
released on every path.

## Actual
Every failure upstream is collapsed into an empty list by
`LichessClient.fetch_user_games` (`lichess_client.py:85-98`), and `api.py` maps an empty
list to a **200**:

```python
# backend/api.py:212-214
raw_games = client.fetch_user_games(username, max_games=max_games)
if not raw_games:
    return {"status": "no_games", "message": "No new games retrieved or rate limit hit.", "count": 0}
```

versus the success path:

```python
# backend/api.py:271-275
return {
    "status": "success",
    "synced_games": synced_games,
    "new_blunders": new_blunders_count
}
```

The two shapes share only `status`. Observed:

```
HTTP 200 {'status': 'no_games', 'message': 'No new games retrieved or rate limit hit.', 'count': 0}
```

A rate-limit (429), a revoked token, and a genuinely empty account are indistinguishable.
The *other* two sync entry points use a third shape — `repertoire.py:1434-1437` returns
`{"status": "no_games", "synced_games": 0, "total_games": N}` and
`repertoire.py:1679-1683` returns `{"status": "no_games", "synced_games": 0,
"new_blunders": 0, "total_games": N}`. Three shapes for one operation.

And the error path leaks:

```python
# backend/api.py:261-269
blunders = analyzer.analyze_game_openings(g)     # can raise EngineTerminatedError /
if blunders:                                     # FileNotFoundError / OperationalError
    analyzer.save_blunders_to_db(blunders)
...
analyzer.close()     # 268 — skipped on exception
conn.close()         # 269 — skipped on exception
```

There is no `try/finally`, so a single failing game leaks one Stockfish process **and** one
SQLite connection for the lifetime of the server.

## Root cause
No error taxonomy and no `try/finally` around an acquired resource. `fetch_user_games`
returns `List[Dict]` where `[]` means both "no games" and "request failed", so the caller
cannot tell them apart.

## Exploit / escalation
1. Revoke the Lichess token → `get_account_profile()` returns `None` → `/api/sync` 400s,
   but if the token is *rate-limited* or Lichess returns 5xx, `/api/sync` returns 200
   `no_games` and the UI shows "nothing new".
2. On a fresh DB, CODE-02-01 makes `save_blunders_to_db` raise on the **first** blunder →
   each of the 30 games leaks a process + a connection → 30 leaked Stockfish processes in
   one request (compounds CODE-02-09).
3. Adjacent: the `INSERT OR REPLACE INTO games` at `api.py:245-256` is a `DELETE`+`INSERT`
   in SQLite. Because `PRAGMA foreign_keys` is off (see CODE-02-20) nothing cascades today,
   but if it were ever enabled this statement would silently delete every `blunders` row
   for that game.
