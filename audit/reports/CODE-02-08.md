# CODE-02-08 — The startup migration's `LEFT JOIN study_moves` has no usable index: measured `SCAN sm` per `repertoire_moves` row
- **Severity:** high
- **Type:** spec-violation (perf cliff)
- **File:** `backend/db.py`
- **Line(s):** 169-179 (`study_moves` DDL), 326-364 (the join), 254-262 (the restore join)
- **Component:** Startup migration
- **Repro script:** `audit/scripts/CODE-2_repro.py` (PROBE 5)
- **Detected by:** CODE-2

## Expected
Any join predicate that is evaluated per row should be backed by an index whose leading
column is constrained by the query.

## Actual
`study_moves` declares only a composite **primary key that leads with `study_id`**:

```python
# backend/db.py:170-179
CREATE TABLE IF NOT EXISTS study_moves (
    study_id INTEGER NOT NULL,
    repertoire TEXT NOT NULL,
    parent_fen TEXT NOT NULL,
    move_uci TEXT NOT NULL,
    PRIMARY KEY (study_id, repertoire, parent_fen, move_uci),
    FOREIGN KEY(study_id) REFERENCES repertoire_studies(id) ON DELETE CASCADE
)
```

but the purge joins **without** `study_id`:

```python
# backend/db.py:327-332
cursor.execute("""
SELECT rm.id, rm.parent_fen, rm.fen, sm.study_id
FROM repertoire_moves rm
LEFT JOIN study_moves sm ON sm.repertoire = rm.repertoire
    AND sm.parent_fen = rm.parent_fen AND sm.move_uci = rm.move_uci
WHERE rm.repertoire = ?
""", (rep,))
```

`PRIMARY KEY (study_id, repertoire, parent_fen, move_uci)` is a *unique index* whose first
column is unconstrained here, so SQLite cannot seek. Measured plan:

```
index on study_moves: {'seq': 0, 'name': 'sqlite_autoindex_study_moves_1',
                       'unique': 1, 'origin': 'pk', 'partial': 0}

-- plan for the migration LEFT JOIN (db.py:330) --
    SEARCH rm USING INDEX sqlite_autoindex_repertoire_moves_1 (repertoire=?)
    SCAN sm LEFT-JOIN
```

`SCAN sm LEFT-JOIN` is a **full table scan of `study_moves` for every row of
`repertoire_moves`** → O(|repertoire_moves| × |study_moves|). Combined with CODE-02-07
(runs twice per boot) this is a quadratic startup cost on exactly the tables the user is
actively growing.

The same missing index makes the `UPDATE ... SET study_name = (SELECT ...)` correlated
subquery at `db.py:301-318` uncacheable, and `repertoire.py` re-derives the same
3-token join in at least 8 other places.

Additionally, the BFS itself is quadratic in the *queue*:

```python
# backend/db.py:349-350
while queue:
    curr = queue.pop(0)
```

`list.pop(0)` is O(n), so a long line is O(n²) just in the deque.

## Root cause
The table's only index is the PK, which is not aligned with the only way the application
joins it. There is no `CREATE INDEX` statement anywhere in the repository
(`grep -rn "CREATE INDEX" --include=*.py .` → zero hits), so every non-PK predicate in the
schema is a scan.

## Exploit / escalation
1. Grow the repertoire to a few thousand moves (routine for a Chessbook-style study with
   both colours and many branches) and restart: startup time grows super-linearly and the
   app appears hung before the port opens.
2. Since the join result decides `study_move_ids` — the set of moves **exempted** from
   deletion (CODE-02-07) — a slow/absent index directly governs whether user moves are
   deleted. Any future `ANALYZE`/index change that alters the plan changes deletion
   semantics.
3. Adjacent: `repertoire_studies` `UNIQUE(name, repertoire)` and
   `repertoire_moves UNIQUE(repertoire, parent_fen, move_uci)` do get indexes, so the
   asymmetry is easy to miss when reading the DDL.
