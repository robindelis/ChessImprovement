# CODE-05-02 — The user's entire production database is committed to git (and `.gitignore` is untracked, so it protects nothing)
- **Severity:** critical
- **Type:** security
- **File:** `chess_improvement.db`
- **Line(s):** n/a (binary blob, tracked)
- **Component:** Repo hygiene / production data
- **Repro script:** `audit/scripts/CODE-05_repro_initdb_purge.py`, `audit/scripts/CODE-05_repro_purge_rootcause.py`
- **Detected by:** CODE-5

## Expected
`chess_improvement.db` is untracked and git-ignored, exactly as `AGENTS.md:277-279` demands:
> **CRITICAL PRODUCTION DATA INVARIANT**: The production database `chess_improvement.db` stores user `RobiDeli`'s actual games, blunders, and personal repertoire studies. Under NO circumstances should automated tests, adversarial probes, or developer scripts modify or pollute this database!

## Actual
The database is a tracked git object, committed in `81f4ed6`, and `git status` reports it as modified:

```
$ git ls-files | grep chess_improvement
chess_improvement.db
$ git status --porcelain | grep chess_improvement
 M chess_improvement.db
```

Reading the committed blob read-only (`git show HEAD:chess_improvement.db > /tmp/...; sqlite3 file:...?mode=ro&immutable=1`) shows the user's real private data is in permanent history:

```
=== HEAD (committed) ===
  games: 298
  blunders: 153
  repertoire_moves: 243
  drill_reviews: 153
  explorer_cache: 156
  scouted_content: 14
  settings: 5          (key 'lichess_username' = 'RobiDeli')

=== sample of the personal repertoire inside the committed blob ===
  ('white', 'Caro-Kann Defense', 3)
  ('white', 'French Defense', 2)
  ('white', "King's Pawn Game", 2)
  ('black', "King's Indian Defense: Normal Variation", 3)
  ('black', "King's Indian Defense: Orthodox Variation", 3)
  ('black', "Sicilian Defense: Dragon Variation, Yugoslav Attack", 3)
```

Full SAN move lists are present too (`'TjPP88Uq', 'c4 Nf6 Nc3 g6 g3 Bg7 Bg2 d6 Nf3 O-O d4 Nc6 O-O e5 d5 Nb8 e4 Nbd7 ...'`), and opponent usernames (`jecero`, `ivan_ermolaev`, `marcopolo777`, …).

`.gitignore` — which is meant to be the control for this — is **not tracked**:

```
$ git status --porcelain | grep gitignore
?? .gitignore
```

So the file exists only in this working tree; a fresh `git clone` gets the database and *not* the ignore rules.

## Root cause
The database lives at the repository root (`backend/db.py:7`):
```python
DEFAULT_DB_PATH = os.path.join(os.path.dirname(os.path.dirname(os.path.abspath(__file__))), "chess_improvement.db")
```
i.e. inside the git work tree, and was committed before `.gitignore` existed. `.gitignore` was authored later and never staged, so `node_modules/`, `__pycache__/`, `*.pyc` are *also* still tracked (see CODE-05-13) — adding a `.gitignore` does not untrack already-tracked paths.

## Exploit / escalation
1. `git clone` → `sqlite3 chess_improvement.db` → 298 real rated games with full move lists, 153 analysed blunders, and the user's private 243-move opening repertoire. This is exactly the data `AGENTS.md` §9.3 declares untouchable private study material.
2. The 243 repertoire moves are **still recoverable** from `81f4ed6` even though the working-tree copy has been reduced to `repertoire_moves: 0` (see CODE-05-03) — the "loss" in the worktree is a false sense of security; the data is still in history.
3. Adjacent variants with the same root cause (binary/derived state inside the tracked tree):
   - `bin/stockfish/stockfish-linux-x86-64-universal` — a 103 MB stripped ELF committed as a git blob.
   - `backend/__pycache__/*.pyc` and `tests/__pycache__/*.pyc` — 15 compiled files, all listed as ` M` in `git status`, i.e. they churn on every run and will bloat/confuse every future diff.
   - `node_modules/` — 555 files including 99 Electron `dist/` binaries, so the repo is 401 MB of which ~203 MB is `.git`.
