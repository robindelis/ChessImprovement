# CODE-02-13 — A global `@app.exception_handler(ValueError)` turns every internal `ValueError` in the app into a 400 whose body is the raw exception string
- **Severity:** medium
- **Type:** security / wrong-result
- **File:** `backend/api.py`
- **Line(s):** 50-54
- **Component:** Exception handling
- **Repro script:** `audit/scripts/CODE-2_routes.py` (section 3)
- **Detected by:** CODE-2

## Expected
Application-level validation failures should be 400/422 with a curated message. Internal
errors (a bad SQL column, a corrupted record, a `chess` parse failure deep in a helper)
should be 500 with a generic body and a server-side log.

## Actual
```python
# backend/api.py:50-54
@app.exception_handler(ValueError)
async def value_error_handler(request, exc: ValueError):
    if "Out of range float values" in str(exc):
        return JSONResponse(status_code=422, content={"detail": "Invalid float value: NaN and Infinity are not allowed."})
    return JSONResponse(status_code=400, content={"detail": str(exc)})
```

Starlette's `ExceptionMiddleware` walks the handler map by class hierarchy, so this
catches a `ValueError` raised **anywhere** in the app — including inside `chess`'s parsers,
`json`, and any `int()`/`float()` conversion in `api.py:176-178` or deep inside
`repertoire.py`.

Demonstrated by making a manager method raise a realistic internal `ValueError`:

```
  /api/repertoire/tree -> 400 {"detail":"no such column: totally_internal_secret_schema_detail"}
```

A schema error is reported to the browser as a client mistake with the SQL detail
verbatim.

Two further consequences:

1. The handler intercepts `ValueError`s raised for *bad server state* as well as for *bad
   input*. `GET /api/settings` re-reads and coerces the **stored** settings with no guard
   (`api.py:176-178`):
   ```python
   max_opening_ply: int(get_setting("max_opening_ply", "24")),
   blunder_threshold_cp: int(get_setting("blunder_threshold_cp", "150")),
   gap_threshold: float(get_setting("gap_threshold", "5.0"))
   ```
   A corrupt `settings` row therefore produces
   `400 {"detail":"invalid literal for int() with base 10: 'abc'"}` and, because there is
   no `try/except` around those three calls, the whole Settings page is dead.
2. Because the handler is registered for the *bare* `ValueError`, it also swallows
   `ValueError`s that a route intended to be a 500, so a server-state failure is reported
   to the client as a client error with no log line — real outages become invisible.

## Root cause
The handler exists to normalise one Pydantic message ("Out of range float values") but is
scoped to the whole exception class instead of being applied at the single boundary that
produces that message. The `str(exc)` body is an unconditional reflection of the
exception.

## Exploit / escalation
1. `POST /api/sync` and every sync stream call `analyze_game_openings`, which does
   `int(get_setting("max_opening_ply", "24"))` and `int(get_setting("blunder_threshold_cp", "150"))`
   (`analyzer.py:97-98`). A corrupt settings value makes **every** analysis request 400
   with the raw `int()` message, while the UI reports "sync failed" with no diagnosis.
2. `except Exception as e: raise HTTPException(400, str(e))` appears in seven scout routes
   plus `api.py:1051, 1065, 1074, 1083, 1098, 1107, 1116` — a second, independent raw
   exception reflection path. Any `yt-dlp` or network error message from `scout.py` is
   returned to the browser verbatim.
3. Adjacent: the same seven `except Exception` blocks also swallow genuine 5xx causes
   (a `sqlite3.DatabaseError` from a locked DB is an `Exception`), so a server-side
   infrastructure failure is reported to the client as a 400 "bad request" with no log
   line.
