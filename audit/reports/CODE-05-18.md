# CODE-05-18 — `tests/__init__.py` is untracked, so a fresh clone cannot import the isolation module every test depends on
- **Severity:** low
- **Type:** spec-violation
- **File:** `tests/__init__.py`
- **Line(s):** 1-6
- **Component:** Test suite / repo hygiene
- **Repro script:** `git status --porcelain` (see "Actual")
- **Detected by:** CODE-5

## Expected
Every module a test imports is tracked. `tests/test_setup.py` is mandated by `AGENTS.md:282-288` §9.1 and by `audit/BRIEF.md` hard rule 2, so it and its package marker must exist in a clone.

## Actual

```
$ git status --porcelain | grep tests/
?? tests/__init__.py
?? tests/attacker_round2_creative_probe.py
?? tests/attacker_security_probe.py
?? tests/test_pedagogical_trainer.py
?? tests/test_setup.py
?? tests/test_studies.py
?? tests/test_trainer_hint_and_line_completion.py
?? tests/test_user_behavior_probe.py
```

Seven files that the current 104-test result depends on are untracked, including `tests/test_setup.py` (the isolation module) and `tests/test_studies.py` (7 tests). `git ls-files tests/` shows only 16 of the 23 files present.

```
$ git ls-files tests/ | wc -l
16
$ ls tests/*.py | wc -l
23
```

The tracked set also includes the 9 attack scripts while omitting `tests/__init__.py`, i.e. exactly inverted from what should be tracked.

Note that Python 3.3+ namespace packages let `import tests.test_setup` succeed even without `__init__.py`, so this does not break the suite today — but `tests/__init__.py` currently contains the 6 lines that make `tests` a *regular* package, and `unittest discover tests` (the command `AGENTS.md:37` and `package.json:11` both mandate) relies on the discovery/top-level-dir relationship that the explicit `__init__.py` stabilises. Its absence is a latent, order-of-imports-dependent breakage rather than an active one.

## Root cause
Files were created with `Write` and never `git add`-ed, in the same session that produced the untracked `.gitignore` (CODE-05-12) and the untracked `audit/` tree. There is no `git add -A` / commit discipline in the workflow and no pre-commit hook.

## Exploit / escalation
1. `git clone` → `python -m unittest discover tests` → `ModuleNotFoundError: No module named 'tests'` is not raised (namespace packages save it), but `tests/test_setup.py` is simply **absent**, so every `import tests.test_setup` raises `ImportError` and the whole suite fails to collect. The failure mode on a clone is "cannot import", not "isolation missing" — easy to misdiagnose as a backend problem.
2. If someone "fixes" the clone failure by creating a fresh `tests/test_setup.py` from `AGENTS.md:282-288`'s snippet, they get a version that does **not** copy the production DB and does **not** clear the repertoire tables — changing the observable baseline of `tests/test_repertoire.py:143-155` (see CODE-05-07) without anyone noticing.
3. Adjacent variants with the same root cause (untracked files the suite depends on):
   - `tests/test_pedagogical_trainer.py`, `tests/test_trainer_hint_and_line_completion.py`, `tests/test_user_behavior_probe.py`, `tests/test_studies.py` — 20 of the 104 tests are untracked, so `AGENTS.md`'s "all tests must pass" gate is unverifiable from a clone.
   - `audit/BRIEF.md`, `audit/STATE.md`, `audit/reports/`, `audit/patches/`, `audit/scripts/` are all untracked, so the audit itself is not reproducible from the repository.
   - `.gitignore` is untracked, so nothing currently prevents any of the above from being either lost or committed inconsistently.
