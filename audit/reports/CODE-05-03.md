# CODE-05-03 — `init_db()` boot migration silently deletes 155 of the user's own prepared moves and injects the three default studies `AGENTS.md` §9.3 forbids
- **Severity:** critical
- **Type:** data-loss
- **File:** `backend/db.py`
- **Line(s):** 237, 244-404 (destroying step at 322-364; study injection at 366-404)
- **Component:** Startup / DB migration (`start.py:19`)
- **Repro script:** `audit/scripts/CODE-05_repro_initdb_purge.py`, `audit/scripts/CODE-05_repro_initdb_purge_detail.py`, `audit/scripts/CODE-05_repro_purge_rootcause.py`
- **Detected by:** CODE-5

## Expected
`AGENTS.md:299-307` §9.3:
> User `RobiDeli` currently trains and maintains two specific White opening studies: … Anti French Defense … Caro-Kann Fantasy Variation … **DO NOT seed default lines (*Italian Game*, *Open Sicilian*, *French Defense 3. Nc3*, *Sicilian Dragon*, *King's Indian Defense*) into the user's production repertoire.**

A schema migration must be additive. It must never `DELETE` the user's repertoire, and it must never relabel the user's moves as "Italian Game" / "Sicilian Dragon" / "King's Indian Defense".

## Actual
Running the real `init_db()` **once** against a `/tmp` copy of the git-committed production DB (the production file was opened `mode=ro&immutable=1` and never written) destroys 65% of the personal repertoire:

```

after a single init_db() boot: {'repertoire_moves': 86,  'repertoire_studies': 3, 'study_moves': 86, ...}
```

```
moves before boot: 243
moves after  boot: 86
DESTROYED        : 157
ADDED            : 0
>>> how many of the destroyed moves were USER moves?
    155 of 157 destroyed rows were is_user_move=1 (the user's own prepared moves)
```

And it injects exactly the forbidden default studies, then re-labels every surviving user move as one of them:

```
### studies the migration INJECTED (violates AGENTS.md 9.3) ###
    ('Italian Game', 'white', 'Italian Game and Classical White lines')
    ('Sicilian Dragon', 'black', 'Sicilian Dragon Variation vs 1.e4')
    ("King's Indian Defense", 'black', "King's Indian Defense vs 1.d4")

### study_name re-labelled onto the surviving moves ###
    'Italian Game'                   52
    'Sicilian Dragon'                19
    "King's Indian Defense"          15
```

Note the mechanism: the committed DB has **no** `repertoire_studies`/`study_moves` tables, so `study_move_ids` in the purge is empty and nothing is protected.

## Root cause
`backend/db.py:237` — `init_db()` calls a **destructive** migration on every boot, and `start.py:19` calls `init_db()` unconditionally before serving:

```python
# Migration: Purge isolated blunder moves and initialize default studies
try:
    migrate_studies_and_cleanup_blunders(conn)
```

Step 3 of that function (`backend/db.py:346-364`) is a reachability BFS that only walks forward from the start position, then deletes everything it did not reach:

```python
queue = [start_3]
visited = set()
reachable_ids = set()
while queue:
    curr = queue.pop(0)
    ...
    for m_id in parent_map.get(curr, []):
        reachable_ids.add(m_id)
        dest = dest_map.get(m_id)
        if dest and dest not in visited:
            queue.append(dest)

all_ids = set(r["id"] for r in rows)
orphan_ids = all_ids - reachable_ids - study_move_ids
if orphan_ids:
    placeholders = ','.join('?' for _ in orphan_ids)
    cursor.execute(f"DELETE FROM repertoire_moves WHERE id IN ({placeholders})", tuple(orphan_ids))
```

`CODE-05_repro_purge_rootcause.py` instruments this exact BFS and shows the destroyed rows are **side-line fragments**, not garbage — every orphan parent position is the `fen` of *zero* other rows, i.e. the user's own variations entered out of tree order, which `AGENTS.md:134` describes as a first-class feature ("Stepping back or undoing moves and playing alternatives automatically branches into new variations"):


Step 4 (`backend/db.py:366-404`) then unconditionally creates the three forbidden studies when `repertoire_studies` is empty and overwrites `study_name` on every surviving move.

## Exploit / escalation
1. Any user whose repertoire contains a side line, an imported scout line, or a fragment whose parent move is absent from `repertoire_moves` loses it silently on the next app launch — no confirmation, no backup, no log line.
2. The failure is *silent by design*: `init_db()` wraps the migration in `try/except Exception as e: print(...)` (`backend/db.py:236-239`), and the purge itself has no logging at all, so the user sees the moves simply vanish from the UI.
3. Adjacent variants with the same root cause (boot-time mutation of user data without a guard):
   - the same `init_db()` also rewrites every `explorer_cache` row to the white-perspective eval convention (`backend/db.py:210-228`) — an unbounded `SELECT` + per-row `UPDATE` on every single boot, over 444 rows and growing.
   - `repertoire_moves` rows are also destroyed by `RepertoireManager.add_repertoire_move` (`backend/repertoire.py:477-525`), which on every `is_user_move` insert `DELETE`s the existing user move at that position and recursively prunes its subtree — so a single wrong click in the builder is as destructive as the migration.
   - because the data is in git (`CODE-05-02`), recovery is possible today via `git show 81f4ed6:chess_improvement.db`; after history is cleaned it will not be.
