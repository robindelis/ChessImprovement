# CODE-05-16 — `frontend/vendor/chess.min.js` is an unversioned, uncredited, integrity-unchecked third-party build loaded as a global
- **Severity:** low
- **Type:** security
- **File:** `frontend/vendor/chess.min.js`
- **Line(s):** 1 (whole file, 15 141 bytes)
- **Component:** Frontend dependency
- **Repro script:** static inspection (see "Actual")
- **Detected by:** CODE-5

## Expected
A vendored dependency records its upstream project, version, licence and a hash, so a future maintainer can tell what they are shipping and whether the file was tampered with. `AGENTS.md:73` describes it only as:
> `vendor/  # Vendored client dependencies (chess.min.js)`

## Actual
The file has **no banner, no version string, no licence, no provenance comment, and no SRI hash** anywhere — the entire header is minified code:

```
$ head -c 200 frontend/vendor/chess.min.js
```

It is loaded with no `integrity` attribute and no `crossorigin`:
```html
8:    <script src="/vendor/chess.min.js"></script>
```
and it is a UMD build that assigns a **global** `window.Chess` in the browser (`"undefined"!=typeof exports&&(exports.Chess=Chess)`), so it shares the global scope with `board.js`, `repertoire_builder.js`, `scout.js` and `app.js`.

It is a genuine, working `chess.js`-family library — the API surface the frontend needs is present and behaves correctly:

Its size (15 KB, minified) and its 2016-era API (`load`/`put`/`remove`, `moves({verbose})`) identify it as `chess.js` 0.10.x, not the modern 1.x rewrite — a materially older dependency than the rest of the stack (Electron 44, Python 3.14).

Nothing in the repo records this: no `package.json` entry (the only declared dependency is `electron: ^44.4.5`), no `requirements.txt`, no `LICENSE`/`THIRD_PARTY_NOTICES`, and no `npm ls` entry. `AGENTS.md:24` lists the Python deps inline in prose but there is no lock file for them either.

## Root cause
The file was downloaded and committed without provenance metadata, and there is no dependency-manifest convention in the repo. `audit/BRIEF.md` rule 5 and `AGENTS.md:203` ("zero bundlers, zero build step") make manual vendoring the intended workflow, but nothing in the documented workflow requires recording what was vendored.

## Exploit / escalation
1. Because there is no hash or version pinned anywhere, a tampered or silently upgraded `chess.min.js` is undetectable by review: it is a single untyped 15 KB blob, and `tests/test_timeline_spam.py:55` is the only automated consumer, which merely `require()`s it and never asserts on it.
2. It runs in the Electron renderer described in CODE-05-09 — same origin as the rest of the app, full DOM and `fetch` access, plus the preload bridge — so a supply-chain substitution here is full renderer compromise.
3. Adjacent variants with the same root cause (undeclared, unversioned dependencies):
   - `package.json:16-18` declares `electron: ^44.4.5` but no `engines`, no lockfile-integrity assertion, and `run-desktop.sh:8` hardcodes `/home/robin/miniconda3/bin` — the Python side is entirely unpinned.
   - `frontend/vendor/` contains exactly one file and `frontend/assets/pieces/` exactly 12; there is no `vendor/README` or manifest, so the next vendored library will be added the same way.
   - The 5 `openings_data/*.tsv` files (388 KB of ECO data) have no provenance or licence recorded either, and `backend/openings.py:7` loads them from a path relative to the source tree with no integrity check.
