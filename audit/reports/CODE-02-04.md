# CODE-02-04 — `POST /api/sync` marks games `analyzed_at` **before** analysis and commits, so any analysis failure permanently suppresses that game's blunders forever
- **Severity:** high
- **Type:** data-loss
- **File:** `backend/api.py`
- **Line(s):** 198-275 (skip guard 226-229, insert 245-257, analysis 259-264)
- **Component:** `POST /api/sync` (orphaned duplicate sync pipeline)
- **Repro script:** `audit/scripts/CODE-2_freshdb.py` (interacts with CODE-02-01)
- **Detected by:** CODE-2

## Expected
`games.analyzed_at` is the "do not re-analyse" flag (`AGENTS.md` §5.1: *"0 if pending"*).
It must be set only **after** a successful analysis, and the DB row must be written after
the analysis succeeds, so that an interrupted/failed analysis leaves the game pending.

## Actual
The flag is written and committed *first*:

```python
# backend/api.py:226-229  (skip guard)
cursor.execute("SELECT id, analyzed_at FROM games WHERE id = ?", (game_id,))
existing = cursor.fetchone()
if existing and existing["analyzed_at"] > 0:
    continue

# backend/api.py:245-257  (write + commit, analyzed_at = NOW)
cursor.execute("""
INSERT OR REPLACE INTO games (
    id, speed, rated, played_at, white_player, black_player,
    white_rating, black_rating, user_color, result, opening_name, eco, moves_san, analyzed_at
) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
""", (
    game_id, g.get("speed"), 1 if g.get("rated") else 0,
    g.get("createdAt", int(time.time())),
    white_user, black_user,
    white_rating, black_rating,
    user_color, result, opening_name, eco, moves, int(time.time())
))
conn.commit()

# backend/api.py:259-264  (analysis happens AFTER the commit)
g["user_color"] = user_color
blunders = analyzer.analyze_game_openings(g)
if blunders:
    analyzer.save_blunders_to_db(blunders)
```

Any failure between the `conn.commit()` on line 257 and the end of the loop body —
`EngineTerminatedError` from Stockfish, `FileNotFoundError` for a missing binary, the
`best_pv` `OperationalError` from CODE-02-01, `Ctrl-C`, or an OOM kill — leaves the row with
`analyzed_at > 0` and no blunders. Every subsequent sync skips it at line 228. **The blunders
for that game can never be recovered by re-syncing.**

Note that the *live* paths in `backend/repertoire.py:1824-1835` have the same ordering, and
additionally use `INSERT OR REPLACE ... analyzed_at = int(time.time())` (line 1832) — so the
same permanent-suppression applies to the frontend's *Sync & Analyze* button.

Compounding: the route is **frontend-orphaned** (`grep -rn "api/sync" frontend/` → no
hits; only `tests/test_api.py:194`, `tests/repro_bugs.py:136`,
`tests/verify_patches.py:104` call it), and it is a 78-line third copy of the sync
pipeline already implemented at `api.py:404-424` → `repertoire.sync_recent_games` /
`stream_sync_recent_games` / `analyze_user_games` / `stream_analyze_user_games`.

## Root cause
The persistence flag and the "work is done" flag are the same column, and it is committed
before the work. There is no `analyzing`/`failed` state and no requeue of rows whose
`analyzed_at` was set but whose blunder set is empty.

## Exploit / escalation
1. Delete/rename `bin/stockfish/stockfish-linux-x86-64-universal` (or break it), run one
   sync of 30 games, restore the binary, sync again → all 30 games are permanently skipped
   and `GET /api/repertoire/game_gaps` reports `total_games_analyzed: 30` with zero gaps.
2. On a fresh DB (CODE-02-01) *every* game ends up in this state after the first failed insert.
3. Adjacent variant: `POST /api/sync` is unauthenticated and has no rate limit; each call
   spawns a new `GameAnalyzer` → a new Stockfish process (see CODE-02-09), and each call
   re-runs the full `INSERT OR REPLACE` (which is a `DELETE`+`INSERT` in SQLite), so a
   concurrent `/api/repertoire/sync_games_stream` and `POST /api/sync` race on the same rows.
