# CODE-05-07 — The test suite is coupled to a copy of the user's real database: one test hardcodes the user's game count and six assertion blocks go vacuous without it
- **Severity:** medium
- **Type:** spec-violation
- **File:** `tests/test_setup.py`
- **Line(s):** 31-41 (production copy), `tests/test_repertoire.py:143-155`
- **Component:** Test suite / isolation
- **Repro script:** `audit/scripts/CODE-05_repro.py`
- **Detected by:** CODE-5

## Expected
`AGENTS.md:288` describes `tests.test_setup` as creating "a dedicated temporary copy (`/tmp/chess_test_*.db`)". A test suite that seeds its own fixtures is hermetic: same result on a fresh clone, on CI, and on the author's machine.

## Actual
`tests/test_setup.py:31-41` clones the **entire production database** into the temp DB:

```python
    # Copy production DB contents (games, blunders, explorer_cache, settings) if it exists
    prod_db = getattr(db_mod, "DEFAULT_DB_PATH", os.path.join(PROJECT_ROOT, "chess_improvement.db"))
    if os.path.exists(prod_db):
        try:
            src = sqlite3.connect(prod_db)
            dst = sqlite3.connect(temp_path)
            src.backup(dst)
```

Consequently the suite's result depends on how many rated games `RobiDeli` happens to have. `tests/test_repertoire.py:143-145` hardcodes that count:

```python
    def test_all_games_scan_and_count(self):
        total_cnt = self.rm.get_total_games_count()
        self.assertGreaterEqual(total_cnt, 280)
```

Re-pointing `DEFAULT_DB_PATH` at a nonexistent file before `tests.test_setup` imports (temp DB then contains 0 games / 0 blunders) breaks it:

```
OK  tests.test_setup DID isolate onto a temp DB path
    CHESS_DB_PATH = /tmp/chess_test_1gpzpqhd.db
    temp DB games=0 blunders=0  <-- production copy SKIPPED

=== RESULT (temp DB with NO production data) ===
run=104 failures=1 errors=0
  FAIL tests.test_repertoire.TestRepertoire.test_all_games_scan_and_count
        AssertionError: 6 not greater than or equal to 280
```

Note `6` — only the rows the tests themselves inserted. The other 103 tests pass, but as shown in CODE-05-06 the *assertions* that would have failed are all wrapped in data-dependent guards (`if gaps:`, `if unpatched["patched_count"] > 0:`, `if len(data["games"]) > 0:`, `if games:`, `if top_move_w.get("eval") is not None:`), so on an empty DB they silently degrade to no-ops rather than failing loudly.

Two tests additionally require **live network** to the Lichess opening explorer (`tests/test_repertoire.py:14-23`, `:131-141`, `:305-324` all call `get_candidate_moves_2000`, which is only backed by `explorer_cache` for FENs the user happened to visit).

## Root cause
`tests/test_setup.py` treats the production DB as a fixture source rather than a source of *schema*. Copying user rows into the test DB makes the suite non-hermetic and couples pass/fail to the user's Lichess history — and it is also the reason 153 real blunders are visible to every test, so data-dependent bugs (e.g. cpl_loss ordering) can only ever be validated against one person's games.

## Exploit / escalation
1. A contributor without `chess_improvement.db` (i.e. everyone but the author, since the DB is committed but a fresh clone may not include it after CODE-05-02 is fixed) gets a red suite out of the box, or — after the conditional guards are removed — a different one.
2. A user who syncs 300+ games makes `assertGreaterEqual(total_cnt, 280)` pass; a user who prunes to fewer than 280 games, or an environment where the `src.backup(dst)` at `test_setup.py:37` fails (its `except Exception` only prints a warning, line 40-41), sees the suite fail for reasons unrelated to the code.
3. Adjacent variants with the same root cause:
   - `tests/test_setup.py:40-41` — a failed production copy only prints `"Warning: Failed to copy production DB to test DB"`, so the suite proceeds in a silently degraded state rather than aborting.
   - `tests/test_setup.py:58-59, 65-66, 71-72, 82-83` — four bare `except Exception: pass` blocks wrap the repertoire clear and the singleton resets; if any fails, tests run against a *dirty* temp DB and still report OK.
   - `tests/test_setup.py:32` uses `getattr(db_mod, "DEFAULT_DB_PATH", ...)` rather than `db_mod.get_db_path()`, so it snapshots the production path at import time and ignores any `CHESS_DB_PATH` already set by the caller.
