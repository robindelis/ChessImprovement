# CODE-05-11 — `GET /api/repertoire/tree` returns every move under two `parent_fen` keys, so `moves_by_parent` double-counts the whole repertoire
- **Severity:** medium
- **Type:** wrong-result
- **File:** `backend/repertoire.py`
- **Line(s):** 1213-1225 (alias insertion), 1284-1293 (response)
- **Component:** Repertoire API
- **Repro script:** `audit/scripts/CODE-05_repro_tree_duplicate_keys.py`
- **Detected by:** CODE-5

## Expected
`moves_by_parent` is a 1:1 index of the repertoire: `sum(len(v) for v in moves_by_parent.values()) == total_moves`, and each move appears exactly once.

## Actual
`backend/repertoire.py:1213-1225` deliberately inserts a second, *3-token* alias key for every parent that has an en-passant field:

```python
        tree_by_parent = {}
        for m in moves:
            p = m["parent_fen"]
            if p not in tree_by_parent:
                tree_by_parent[p] = []
            tree_by_parent[p].append(m)
            p3 = " ".join(p.split()[:3])
            if p3 != p:
                if p3 not in tree_by_parent:
                    tree_by_parent[p3] = []
                if m not in tree_by_parent[p3]:
                    tree_by_parent[p3].append(m)
```

For a 3-ply line `1. e4 e6 2. d4` — where **no** position has an en-passant square — the endpoint returns 6 keys for 3 moves:

```
### moves_by_parent: 6 keys for 3 moves ###
  tokens=4  rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq -   -> e4
  tokens=3  rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq     -> e4
  tokens=4  rnbqkbnr/pppppppp/8/8/4P3/8/PPPP1PPP/RNBQKBNR b KQkq -  -> e6
  tokens=3  rnbqkbnr/pppppppp/8/8/4P3/8/PPPP1PPP/RNBQKBNR b KQkq    -> e6
  tokens=4  rnbqkbnr/pppp1ppp/4p3/8/4P3/8/PPPP1PPP/RNBQKBNR w KQkq - -> d4
  tokens=3  rnbqkbnr/pppp1ppp/4p3/8/4P3/8/PPPP1PPP/RNBQKBNR w KQkq  -> d4

flattened SAN list: ['e4', 'e4', 'e6', 'e6', 'd4', 'd4']
total_moves field  : 3
DUPLICATED SANs     : {'e4': 2, 'e6': 2, 'd4': 2}
```

The response is internally inconsistent: `total_moves` is `len(moves)` (3) while the index that callers are meant to iterate holds 6 entries. The exact same aliasing exists in the two overlap-detection paths at `backend/repertoire.py:940-947` and `:1178-1185`, so `check_line` / `check_tree` carry a doubled index too.

The frontend happens to survive only because all three consumers do point lookups with an explicit fallback rather than iterating:

```
frontend/repertoire_builder.js:1488:  const candidates = this.treeData.moves_by_parent[parentFen] || this.treeData.moves_by_parent[norm] || [];
frontend/repertoire_builder.js:1916:  const inTreeMoves = (this.treeData?.moves_by_parent?.[normParent]) || [];
frontend/repertoire_builder.js:2145:  const inTreeMoves = (this.treeData?.moves_by_parent?.[normParent]) || [];
```

## Root cause
`normalize_fen` (`backend/repertoire.py:23-29`) keeps **4** tokens (`parts[:4]`, i.e. including en passant), but a large part of the codebase — including this index, the reachability BFS in `backend/db.py:342-344`, and the scout overlap logic — truncates to **3** tokens. Rather than pick one canonical form, the index publishes both. The frontend's `parentFen || norm` fallback at `:1488` is a second, independent encoding of the same ambiguity, so the contract is now defined by three competing conventions.

## Exploit / escalation
1. Any consumer that iterates `Object.values(moves_by_parent)` (a future studies view, a coverage widget, a third-party integration) double-counts every move whose parent has no en-passant square, reporting ~2× the repertoire size.
2. When a position genuinely *has* an en-passant square, `p3 != p` and the move is filed under the 3-token key; two distinct positions that share the first three tokens but differ in en passant (e.g. `... w KQkq e3` vs `... w KQkq -`) **collide** in the same alias bucket, so `moves_by_parent[p3]` can contain moves belonging to different positions. `backend/repertoire.py:1075` and `:999` do `moves_by_parent.get(norm) or moves_by_parent_3.get(norm_3)` and then treat every element as a child of one position.
3. Adjacent variants with the same root cause (mixed 3-token / 4-token FEN keys):
   - `backend/db.py:323-324` seeds the purge BFS with `start_3` (3 tokens) but compares against `dest_map` values built from `r["fen"].split()[:3]`, while the rest of the file (`backend/repertoire.py:23-29`) canonicalises to 4 — the mismatch is what makes the purge in CODE-05-03 over-delete.
   - `tests/test_repertoire.py:157-161` `test_normalize_fen_four_tokens` asserts the 4-token form, and `tests/test_api.py:45-50` `test_repertoire_tree` only asserts `assertIn("coverage_pct", …)` / `assertIn("total_moves", …)` — so no test constrains the index's key count.
