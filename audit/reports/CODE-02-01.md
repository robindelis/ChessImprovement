# CODE-02-01 — `blunders.best_pv` is written by the analyzer but never created by the schema; every blunder insert fails on a fresh database
- **Severity:** high
- **Type:** crash / data-loss
- **File:** `backend/db.py` (schema), `backend/analyzer.py` (writer)
- **Line(s):** db.py:56-90 (`CREATE TABLE blunders` + migrations), analyzer.py:220-241 (`save_blunders_to_db`)
- **Component:** Blunder analysis pipeline / SQLite schema
- **Repro script:** `audit/scripts/CODE-2_freshdb.py`
- **Detected by:** CODE-2

## Expected
Every column that any code path writes or reads must exist in `init_db()`'s
`CREATE TABLE blunders`, or be added by an idempotent `ALTER TABLE` migration.
`AGENTS.md` §5.2 documents the table as the contract.

## Actual
`db.py` never declares `best_pv`:

```python
# backend/db.py:58-83
CREATE TABLE IF NOT EXISTS blunders (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ...
    is_book_move INTEGER DEFAULT 0,
    refutation_pv TEXT,
    explanation TEXT,
    strategic_idea TEXT,
    category TEXT,
    opening_games INTEGER DEFAULT NULL,
    created_at INTEGER,
    FOREIGN KEY(game_id) REFERENCES games(id)
)
```

and the only migration for that table adds `opening_games`, not `best_pv`:

```python
# backend/db.py:86-90
try:
    cursor.execute("ALTER TABLE blunders ADD COLUMN opening_games INTEGER DEFAULT NULL")
except Exception:
    pass
```

but the writer always includes it:

```python
# backend/analyzer.py:226-241
INSERT INTO blunders (
    game_id, move_number, ply, color, fen_before, fen_after,
    played_move, played_san, best_move, best_san,
    eval_before, eval_after, cpl_loss, opening_name, eco,
    is_book_move, refutation_pv, best_pv, explanation, strategic_idea,
    category, opening_games, created_at
) VALUES (?, ...)
```

and two readers depend on it (`api.py:565-571`, `api.py:766-773`).

Building a **brand-new** database with the repo's own `init_db()` and running the
analyzer's INSERT:

```
FRESH DB blunders columns: ['id','game_id','move_number','ply','color','fen_before',
 'fen_after','played_move','played_san','best_move','best_san','eval_before','eval_after',
 'cpl_loss','opening_name','eco','is_book_move','refutation_pv','explanation',
 'strategic_idea','category','opening_games','created_at']
  best_pv present on fresh DB: False
  INSERT with best_pv -> OperationalError: table blunders has no column named best_pv
```

The column only exists in the live `chess_improvement.db` by historical accident (it is
present there, which is why the current test-suite copy of the production DB does not
expose this). Any new machine, any `CHESS_DB_PATH` pointing at a new file, or any
restore-from-backup that predates the column is permanently broken.

## Root cause
`best_pv` was added to `analyzer.py` and to two `api.py` readers, but the corresponding
schema change was never added to `db.py` — and because the production DB happens to
already carry the column, no test ever fails. There is no `PRAGMA user_version`-style
schema version and no column-existence assertion anywhere, so the drift is invisible.

The failure is then **silently swallowed** by the only live caller
(`backend/repertoire.py:1841-1846`):

```python
except Exception as ex:
    print(f"Error analyzing game {game_id}: {ex}")
```

so the UI reports "0 new blunders" and the user's whole blunder/gap-analysis feature
silently produces nothing.

## Exploit / escalation
1. Set `CHESS_DB_PATH` to a new file (fresh install, restore from an older backup) and click
   *Sync Games* in the builder — the engine burns minutes of depth-12 analysis per game and
   **nothing is ever saved**, while the UI reports success.
2. The same INSERT path is reached from `POST /api/sync` (`api.py:262-264`), where the
   `OperationalError` is *not* caught, so the request 500s *and* leaks the Stockfish
   process and the SQLite connection (see CODE-02-11).
3. `GET /api/blunders/{id}` and `POST /api/train/evaluate_move` will fail on any row
   written by a future fixed writer, because they read a key the `SELECT b.*` result
   cannot contain on a fresh DB.
