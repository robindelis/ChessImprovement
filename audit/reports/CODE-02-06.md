# CODE-02-06 — `games.played_at` is written in milliseconds by two writers and in seconds by three others, so `ORDER BY played_at DESC` is globally wrong
- **Severity:** high
- **Type:** wrong-result
- **File:** `backend/api.py`, `backend/repertoire.py`
- **Line(s):** api.py:252, 312, 325-326; repertoire.py:1476, 1568 (ms) vs 1721, 1829 (s)
- **Component:** Recent Games list / schema
- **Repro script:** `audit/scripts/CODE-2_results.py`
- **Detected by:** CODE-2

## Expected
`AGENTS.md` §5.1 declares `played_at` `(INTEGER)`. All writers must use the same unit, and
the reader must not need a magnitude heuristic to interpret it.

## Actual
Two of the five writers emit **milliseconds**, three emit **seconds**:

```python
# backend/repertoire.py:1476 (sync_recent_games) and 1568 (stream_sync_recent_games)
g.get("createdAt", int(time.time() * 1000)),          # milliseconds
```

```python
# backend/repertoire.py:1721 (analyze_user_games) and 1829 (stream_analyze_user_games)
g.get("createdAt", int(time.time())),                 # seconds
```

```python
# backend/api.py:252 (POST /api/sync)
g.get("createdAt", int(time.time())),                 # seconds
```

Note the split is *within the same module and same feature*: `/api/games/sync_recent*`
(ms) vs `/api/repertoire/sync_games*` (s). Lichess's `createdAt` is epoch **milliseconds**,
so the seconds writers only produce a seconds value in the fallback branch — i.e. a game
whose `createdAt` was missing gets a value 1000× smaller than its siblings.

The reader papers over this with a magnitude heuristic:

```python
# backend/api.py:325-326
played_at_raw = row.get("played_at") or 0
played_at_sec = (played_at_raw / 1000.0) if played_at_raw > 1e11 else float(played_at_raw)
```

…but nothing fixes the **sort**, which uses the raw column:

```python
# backend/api.py:312
query += " ORDER BY played_at DESC LIMIT ? OFFSET ?"
```

Observed:

```
Order check: games listed newest-first by stored played_at
   ztest_draws  played_at=1790438401444
   ztest_draw   played_at=1790438401443
   ztest_mixed  played_at=1790438401
  ^ the SECONDS-valued game sorts last although it is the newest by wall clock
```

Any single game written by `POST /api/sync` or `/api/repertoire/sync_games*` while
`createdAt` was absent is buried **permanently** below every millisecond-valued game, and
`GET /api/games/recent?limit=25` will simply never show it again.

## Root cause
No unit contract on the column. Five independent writers each invent their own epoch unit,
and a magnitude sniff (`> 1e11`) is used to compensate at read time instead of normalising
once at write time.

## Exploit / escalation
1. Truncate the `createdAt` value on a handful of NDJSON records (or simply run a sync from
   a Lichess response that omits `createdAt` for old games) → those games vanish from the
   Recent Games list permanently, with no error anywhere.
2. Adjacent: `played_at` is also selected into `get_dashboard`'s `recent_blunders`
   (`api.py:467-472`) and returned to the client raw, so any consumer outside
   `get_recent_games` sees an un-normalised mixed-unit value.
3. Adjacent: `GET /api/games/recent?search=` filters on
   `white_player/black_player/opening_name/eco` only (`api.py:300-303`) — **never on `id`**,
   so a user cannot look up a game by its Lichess ID even though the response contains
   `game_url`.
