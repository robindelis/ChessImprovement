# CODE-02-07 — `init_db()` runs a DELETING repertoire migration on every boot, twice per boot, and commits partial work when it throws
- **Severity:** high
- **Type:** data-loss
- **File:** `backend/db.py`, `backend/api.py`, `start.py`
- **Line(s):** db.py:235-242, 244-364 (purge at 322-364); api.py:74-76; start.py:19
- **Component:** Startup migration
- **Repro script:** `audit/scripts/CODE-2_routes.py` (section 6)
- **Detected by:** CODE-2

## Expected
A data-destructive migration should (a) run exactly once, gated by a schema version; and
(b) roll back on error. A "purge orphans" heuristic must not be a permanent part of
`init_db()`, which is called unconditionally on every process start.

## Actual
`init_db()` unconditionally calls a migration that `DELETE`s user repertoire moves:

```python
# backend/db.py:235-242
# Migration: Purge isolated blunder moves and initialize default studies
try:
    migrate_studies_and_cleanup_blunders(conn)
except Exception as e:
    print(f"Warning in migrate_studies_and_cleanup_blunders: {e}")

conn.commit()
```

and the purge is a reachability BFS from the initial position over a **3-token** FEN key:

```python
# backend/db.py:336-364
parent_map = {}
dest_map = {}
study_move_ids = set()
for r in rows:
    if r["study_id"]:
        study_move_ids.add(r["id"])
    p_3 = ' '.join(r["parent_fen"].split()[:3])
    parent_map.setdefault(p_3, []).append(r["id"])
    dest_map[r["id"]] = ' '.join(r["fen"].split()[:3])

queue = [start_3]
...
orphan_ids = all_ids - reachable_ids - study_move_ids
if orphan_ids:
    placeholders = ','.join('?' for _ in orphan_ids)
    cursor.execute(f"DELETE FROM repertoire_moves WHERE id IN ({placeholders})", tuple(orphan_ids))
```

Three problems:

1. **It runs twice per boot.** `start.py:19` calls `init_db()` in `setup()`, and
   `api.py:74-76` registers a second one:
   ```python
   # backend/api.py:74-76
   @app.on_event("startup")
   def startup_event():
       init_db()
   ```
   So the destructive pass and the (also expensive, see CODE-02-08) full-table scan run
   twice on every launch.

2. **No rollback on error.** The `except Exception` at `db.py:238` only `print`s; the
   unconditional `conn.commit()` at line 241 then commits whatever half of
   `migrate_studies_and_cleanup_blunders` succeeded. A failure in the *middle* of the
   two-repertoire loop (e.g. `dest_map[r["id"]] = ' '.join(r["fen"].split()[:3])`
   raising `AttributeError` on a legacy row with `fen IS NULL`) leaves white already
   purged and black untouched, and that asymmetry is committed.

3. **Any move not reachable from the start position through a *stored* predecessor is
   deleted with no log line.** A user who adds a single move at an arbitrary
   `parent_fen` via `POST /api/repertoire/move` (whose only validation is
   `is_valid_fen`, `api.py:822-823` — the FEN does **not** have to be reachable) and does
   not attach it to a study loses it at the next restart. There is no `print`, no
   `DELETE ... RETURNING`, no dry-run.

## Root cause
A one-off data repair was left in `init_db()` as an unconditional "migration", with no
schema-version gate, no dry-run, no logging, and no transactional boundary. It is
idempotent only in the sense that after the first purge there is nothing left to purge —
which is exactly the problem: it is a silent, repeating DELETE against user data.

## Exploit / escalation
1. `POST /api/repertoire/move` with a legal-but-non-reachable `parent_fen` (e.g. a
   position from a puzzle) → restart the app → the move is gone and no message was
   produced.
2. The same applies to any imported line whose *first* move's `parent_fen` is not the
   standard initial 3-token FEN (some `scout.py` PGN imports start mid-line).
3. Adjacent: `migrate_studies_and_cleanup_blunders` step 4 (`db.py:366-404`) will, on a DB
   with **no** `repertoire_studies` rows but existing moves, create a study literally named
   `"Italian Game"` and relabel every White move with it:
   ```python
   # backend/db.py:375-383
   cursor.execute("INSERT OR IGNORE INTO repertoire_studies (name, repertoire, ...) VALUES (?, 'white', ...)",
                  ("Italian Game", "white", "Italian Game and Classical White lines", now, now))
   ...
   cursor.execute("UPDATE repertoire_moves SET study_name = 'Italian Game' WHERE repertoire = 'white' AND (study_name IS NULL OR study_name = '')")
   ```
   This directly contradicts `AGENTS.md` §9.3 (*"DO NOT seed default lines (Italian Game,
   …) into the user's production repertoire"*) and would mislabel RobiDeli's
   *Anti French Defense* / *Caro-Kann Fantasy* lines as "Italian Game".
