# CODE-05-09 — Electron shell has no navigation lockdown, no CSP, and executes a remote YouTube script in the preload-enabled renderer
- **Severity:** high
- **Type:** security
- **File:** `electron/main.js`
- **Line(s):** 216-261 (`createWindow`), 237 (`loadURL`); `frontend/index.html:921`
- **Component:** Electron desktop shell
- **Repro script:** static grep (see "Actual")
- **Detected by:** CODE-5

## Expected
Per Electron's own security checklist, an app that loads a remote-ish document must: block in-page navigation away from its own origin (`will-navigate`), deny or validate every `window.open`/`target=_blank` (`setWindowOpenHandler` with `{action:'deny'}` + `shell.openExternal` on an allow-listed scheme), and ship a Content-Security-Policy.

## Actual
`electron/main.js` creates the window with the correct three hardening flags:

```javascript
        webPreferences: {
            preload: path.join(__dirname, 'preload.js'),
            nodeIntegration: false,
            contextIsolation: true,
            sandbox: true
        }
```

…and then adds **none** of the navigation guards:

```
$ for h in setWindowOpenHandler will-navigate will-attach-webview new-window \
           web-contents-created "session.setPermission" "shell.openExternal" \
           "app.on('web-contents"; do printf "%-28s %s\n" "$h" "$(grep -c "$h" electron/main.js)"; done
setWindowOpenHandler           0
will-navigate                  0
will-attach-webview            0
new-window                     0
web-contents-created           0
session.setPermission          0
shell.openExternal             0
app.on('web-contents            0
```

There is no CSP anywhere in the project:
```
$ grep -rn "Content-Security-Policy\|http-equiv" frontend/index.html backend/api.py electron/main.js
(no output)
```

and the renderer pulls executable code from a third party on every launch:
```html
921:    <script src="https://www.youtube.com/iframe_api"></script>
```

The app contains four `target="_blank"` links, so Electron's default `window.open` behaviour applies — a **new `BrowserWindow` inheriting the same `webPreferences`, including the preload** — with no handler to deny it:

```
frontend/repertoire_builder.js:1013:  <a href="${g.game_url}" target="_blank" rel="noopener noreferrer" ...>
frontend/repertoire_builder.js:1366:  <a href="${game.game_url}" target="_blank" rel="noopener noreferrer" ...>
frontend/index.html:649:               <a id="btnScoutOpenYoutube" href="#" target="_blank" class="btn-secondary">
frontend/index.html:805:               <a href="https://lichess.org/account/oauth/token" target="_blank" ...>
```

`frontend/index.html:805` is also the one that tells the user where the token lives, and it lacks `rel="noopener"`. The preload surface a navigated-to page would receive (`electron/preload.js:4-13`) is small but non-empty: `window.desktopApp.minimize/maximize/close` (arbitrary window control) and `onSyncGames` (fire the app's Lichess sync action).

Secondary shell defects found in the same file:
- `electron/main.js:249-260` registers `ipcMain.on('window-minimize'/'window-maximize'/'window-close')` **inside** `createWindow()`. `createWindow()` is called again from the macOS `activate` handler (`:305-309`), so every re-activation registers a second set of handlers — each `window-close` then fires `mainWindow.close()` N times.
- `electron/main.js:26-46` `resolveFreePort()` has a classic TOCTOU: it closes the probe server, then `startPythonBackend()` binds the port some time later. Two launches racing each other will both pick the same "free" port and one will fail with `EADDRINUSE`.
- `electron/main.js:61-72` `isServerRunning()` accepts **any** 200–399 from `${SERVER_URL}/api/dashboard` on port 38281 and, in that case, sets `serverStartedByUs = false` and adopts it. Any unrelated local process that answers 200 on that path becomes the app's backend.
- `electron/main.js:125-139` `stopPythonBackend()` is only reached from `window-all-closed`, `before-quit`, `SIGINT` and `SIGTERM`. A `SIGKILL` of Electron, a session logout, or a `start.py` that has itself spawned a Stockfish child leaves orphan processes; the child is not spawned in its own process group, so the `SIGINT` at `:129` is not guaranteed to reach grandchildren.
- `electron/main.js:106-109` pipes the child's stderr into the Electron main process console only. If the backend dies at boot (missing dependency, DB locked, Stockfish absent), the user sees the `Server Startup Timeout` dialog at `:294-297` with the generic text "Please verify that Python and dependencies are installed" and the real traceback is lost.

## Root cause
`createWindow()` hardcodes the target URL and assumes the document never navigates. Nothing in `electron/main.js` models the app's origin, so the standard Electron mitigations were never added, and `frontend/index.html` has no CSP to compensate. `frontend/index.html:921` additionally makes the window's trust boundary depend on a third-party CDN.

## Exploit / escalation
1. `https://www.youtube.com/iframe_api` executes with the app's privileges on every launch. Any compromise or malicious redirect on that origin — or any future removal of TLS enforcement — yields script execution in a window whose preload exposes `window.desktopApp`, from which `desktopApp.onSyncGames(cb)` can be used to trigger `/api/sync` against the user's Lichess account.
2. Because `setWindowOpenHandler` is absent, clicking any of the four `target="_blank"` links spawns a *new* Electron window with the same preload. If `games.id` (interpolated into `game_url` at `backend/api.py:394` and `backend/repertoire.py:1399`) or `study.video_id` (used at `frontend/scout.js:558`) ever carries an attribute-breaking payload, the new window navigates to an attacker origin with the preload attached.
3. Adjacent variants with the same root cause (no `session` hardening, no permission handler):
   - no `session.setPermissionRequestHandler`, so `getUserMedia`/`geolocation` prompts are not programmatically denied;
   - `View → toggleDevTools` is enabled unconditionally in the production menu (`electron/main.js:178`), which is how the CODE-05-04 seed error would ever be seen;
   - `run-desktop.sh` execs `./node_modules/.bin/electron .` with no `--no-sandbox`/`--disable-gpu`/`ELECTRON_DISABLE_SECURITY_WARNINGS` handling, and hardcodes `/home/robin/miniconda3/bin` and `/home/robin/.local/bin` onto `PATH`, so the launcher is machine-specific despite `AGENTS.md:48` describing it as the general entry point.
